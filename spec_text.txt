1. Constitution
The HR system is built on the following immutable principles:
Real authentication via ASP.NET Core Identity – email + password, Remember Me, Forgot Password.
Three Identity roles: HR, DepartmentHead, and Employee.
Department manager is both a data relationship (Department.ManagerId) AND an Identity role (DepartmentHead) – they must always stay in sync.
Every department must have exactly one manager – a non-HR, active, non-deleted Employee in the same department who also holds the DepartmentHead role.
Only DepartmentHeads can assign tasks – HR cannot assign tasks.
Managers cannot be deleted without replacement – HR must assign a new manager first.
Manager replacement is a single transaction that does four things: (1) update Department.ManagerId, (2) remove DepartmentHead role from old manager's ApplicationUser, (3) add DepartmentHead role to new manager's ApplicationUser, (4) optionally proceed with deletion of original manager.
When an employee is soft-deleted, ALL tasks they appear in are also soft-deleted – both tasks they created (AssignedById) and tasks assigned to them (AssignedToId). Silent cascade. Tasks are NOT restored if the employee is later restored.
Soft delete only for Employees and Departments – EmployeeTask has IsDeleted for cascade only.
A Department cannot be soft-deleted while it has active employees.
HR creates both the Employee record and the ApplicationUser account in one transaction when adding a new employee.
All business rules enforced in service layer – Controllers only orchestrate HTTP flow. HR-created employee accounts have IsPasswordChangeRequired = true and must change password on first login before accessing any other page. HTTPS is enforced system-wide via HSTS. All list endpoints are paginated (default 20 per page). DepartmentHead cannot approve their own leave; only HR can. DepartmentHead cannot assign tasks to themselves.
Policy classes centralise reusable rules – Services call policies, not the other way around.
Transactions used for all multi-save operations.
2. System Description
A web-based HR Management System for small organizations. Built as an educational ASP.NET Core 10 MVC project with a clean 3-tier architecture and real authentication via ASP.NET Core Identity.
Core Features
Authentication: login/logout, Remember Me, Forgot Password.
Manage departments (CRUD) – HR only.
Manage employees (CRUD, soft delete) – HR only. Account creation is part of employee creation.
View employees (all by HR, own department by DepartmentHead, own profile by everyone).
Assign tasks – Only DepartmentHeads to their own department members.
Update task status – Only the assigned employee.
Process payroll (monthly, with itemised bonuses/deductions) – HR only.
View payrolls (all by HR, department by DepartmentHead, own by Employee).
Request leave (all employees) – With balance validation (Annual, Sick, Unpaid).
Approve/reject leave requests – HR (all) or DepartmentHead (own department, excluding their own requests).
Self check-in/out – All employees.
Mark team attendance – DepartmentHead (own department).
View attendance reports (all by HR, department by DepartmentHead, own by Employee).
Excluded Intentionally (Future Enhancements)
Audit logging.
Email notifications (Forgot Password uses on-screen token for educational purposes – see Section 11).
Job posting & applicant tracking.

8. Business Rules & Invariants
8.1  Role-Relationship Sync Invariant
Critical Rule — DepartmentHead Must Stay in Sync
The DepartmentHead Identity role and Department.ManagerId are two representations of the same fact.
They MUST always match. Any operation that changes one must change the other in the same transaction:
•  ReplaceManagerAsync:  remove DeptHead role from old manager, add to new manager, update ManagerId.
•  SoftDeleteEmployee:   if employee is a manager, block deletion (force replacement first).
•  CreateEmployee:       if assigned DepartmentHead role, also set Department.ManagerId.
8.2  Account Creation Workflow (HR Creates Employee)
HR fills out the Create Employee form: name, email, department, salary, hire date, role (HR / DepartmentHead / Employee), initial password.
Service opens a transaction.
Employee record is created and saved (gets auto-generated Id).
ApplicationUser is created via UserManager: Email = employee.Email, UserName = employee.Email, EmployeeId = employee.Id.
Initial password is set via UserManager.AddPasswordAsync().
Identity role is assigned via UserManager.AddToRoleAsync().
If role is DepartmentHead: Department.ManagerId is also updated to this employee's Id.
Transaction commits. On any failure, all changes are rolled back.
8.3  Department Manager Invariant
Every department must have exactly one manager at all times.
The manager must satisfy all four conditions:
IsHR = false
DepartmentId == department.Id
IsActive = true
IsDeleted = false
The manager's ApplicationUser must hold the DepartmentHead Identity role.
HR cannot delete an employee who is a department manager. Replacement must come first.
8.4  Manager Replacement Workflow (FR19)
Single Transaction — Four Operations
1. Validate the new manager (same dept, active, non-HR, non-deleted, not current manager).
2. Remove DepartmentHead role from old manager's ApplicationUser (UserManager.RemoveFromRoleAsync).
3. Add DepartmentHead role to new manager's ApplicationUser (UserManager.AddToRoleAsync).
4. Update Department.ManagerId = newManagerId.
All four steps happen inside BeginTransactionAsync(). If any step fails, all are rolled back.
After this succeeds, HR may optionally delete the original manager (now just an Employee).
8.5  Soft-Delete Cascade for Tasks (FR16)
SoftDeleteAsync(employeeId) must soft-delete all EmployeeTask rows where AssignedById = employeeId OR AssignedToId = employeeId, in the same transaction as the employee soft-delete.
Silent — no notification raised. No error if the employee had no tasks.
RestoreAsync(employeeId) does NOT restore cascaded tasks. They remain IsDeleted = true.
All task queries filter: .Where(t => !t.IsDeleted).
8.6  Department Deletion Guard (FR17)
DepartmentService.SoftDeleteAsync rejects if any Employee with DepartmentId = deptId has IsDeleted = false.
Error message: 'Cannot delete department “{Name}”: it still has {count} active employee(s). Reassign or remove them first.'
8.7  Task Rules
Only employees with the DepartmentHead role (checked via User.IsInRole or service) can assign tasks.
Tasks can only be assigned to employees in the same department (TaskAssignmentPolicy).
Status: Pending → InProgress → Completed only. No regression.
Only the assignee (AssignedToId) can update status.
Only the creator (AssignedById) can edit details — only if Status != Completed. A DepartmentHead cannot assign a task to themselves (TaskAssignmentPolicy: AssignedById != AssignedToId). A task is considered overdue when DueDate IS NOT NULL AND DueDate < GETUTCDATE() AND Status != Completed. Overdue tasks are highlighted in the dashboard.
8.8  Payroll Rules
UNIQUE (EmployeeId, Month, Year) — one payroll per employee per month.
BaseSalary is a snapshot; NetSalary = BaseSalary + TotalBonus – TotalDeduction.
Status: Draft → Approved → Paid (no reversal, no editing after Approved).
8.9  Leave Rules
EndDate ≥ StartDate. No overlapping approved leaves. A DepartmentHead cannot approve or reject their own leave request — only HR can action their requests.
Balance checked before submission for Annual/Sick. Unpaid: no limit, no balance row.
On approval: UsedDays += calendar days. On rejection of approved leave: UsedDays -= days.
Auto-create balance row for future years (Annual=20, Sick=10).
8.10  Attendance Rules
UNIQUE (EmployeeId, Date). IsPresent derived from CheckInTime IS NOT NULL.
No double check-in. Check-out requires prior check-in. CheckOut > CheckIn.

9.3  ICurrentUserService  (Scoped)
Now reads identity from ClaimsPrincipal (HttpContext.User), not from session.
public interface ICurrentUserService
{
// Reads the NameIdentifier claim (ApplicationUser.Id)
int  GetCurrentUserId();
// Reads role claims from ClaimsPrincipal
bool IsHR();
bool IsDepartmentHead();
// Loads Employee via ApplicationUser.EmployeeId; cached per request
Task<Employee> GetCurrentEmployeeAsync();
}
// Implementation — one DB hit per request:
private Employee? _cached;
public async Task<Employee> GetCurrentEmployeeAsync()
{
if (_cached != null) return _cached;
var userId = GetCurrentUserId();
var user   = await _userManager.FindByIdAsync(userId.ToString())
?? throw new UnauthorizedException();
_cached = await _db.Employees.FindAsync(user.EmployeeId)
?? throw new NotFoundException("Employee record not found.");
return _cached;
}
9.4  Transaction Handling
CreateEmployeeAsync — transaction: create Employee + create ApplicationUser + assign role (+ update ManagerId if DeptHead).
ReplaceManagerAsync — transaction: remove old role + add new role + update ManagerId.
SoftDeleteEmployeeAsync — transaction: soft-delete Employee + cascade tasks (both FK directions).
ProcessPayrollAsync — transaction: create Payroll + create PayrollItems.
Simple single-entity updates — EF Core default transaction.

11. Authentication
11.1  Identity Configuration (Program.cs)
builder.Services.AddIdentity<ApplicationUser, IdentityRole<int>>(options => {
options.Password.RequiredLength         = 8;
options.Password.RequireUppercase       = true;
options.Password.RequireDigit           = true;
options.Password.RequireNonAlphanumeric = true;
options.Lockout.MaxFailedAccessAttempts = 5;
options.Lockout.DefaultLockoutTimeSpan  = TimeSpan.FromMinutes(15);
options.User.RequireUniqueEmail          = true;
})
.AddEntityFrameworkStores<AppDbContext>()
.AddDefaultTokenProviders();
builder.Services.ConfigureApplicationCookie(options => {
options.LoginPath        = "/Account/Login";
options.AccessDeniedPath = "/Account/AccessDenied";
options.SlidingExpiration = true;
options.ExpireTimeSpan   = TimeSpan.FromDays(14);  // Remember Me
});
11.2  Login Flow
User visits any protected route → redirected to /Account/Login.
User enters email, password, and optionally checks Remember Me.
SignInManager.PasswordSignInAsync(email, password, rememberMe, lockoutOnFailure: true).
On success: if IsPasswordChangeRequired = true, redirect to /Account/ChangePassword (mandatory); otherwise redirect to return URL (or /Employee dashboard).
On failure: show validation error. After 5 failures: account locked for 15 minutes.
11.3  Forgot Password Flow
User visits /Account/ForgotPassword and submits their email.
UserManager.GeneratePasswordResetTokenAsync(user) generates a secure token.
The full reset URL is displayed on the confirmation page (educational shortcut — no email sent).
User copies the link, visits /Account/ResetPassword?email=...&token=...
User enters and confirms new password. UserManager.ResetPasswordAsync() validates token + sets password.
On success: redirect to /Account/Login with success message.

12. Seeding Strategy
12.1  Principles
All seed data uses fixed dates (e.g. new DateTime(2024, 1, 1)). Never DateTime.UtcNow.
EF Core HasData for static data (departments, employees). Identity users seeded in code (not HasData) because UserManager is required for password hashing.
Seed runs in Program.cs on application start if data is absent.
12.2  Migration Steps (Resolving Circular Dependency)
Migration
Action
Migration 1
Create all tables including Identity tables. Department.ManagerId nullable, no FK yet.
Migration 2
Seed Departments (Id=1 HR, Id=2 IT) with ManagerId = NULL. Seed Employees Id 1–15.
Migration 3
UPDATE Departments: set ManagerId=2 (HR dept), ManagerId=3 (IT dept).
Migration 4
ALTER Department.ManagerId to NOT NULL, add FK → Employees(Id).
Migration 5
Seed LeaveBalances for year 2025 for all employees.
Identity Seed (In Code, Not HasData)
Identity users cannot use EF Core HasData because password hashing requires UserManager.
Instead, seed in Program.cs using a helper that runs once if no users exist:
1. CreateAsync(new ApplicationUser { Email = ..., EmployeeId = ... }, password)
2. AddToRoleAsync(user, RoleNames.HR / DepartmentHead / Employee)
Roles (HR, DepartmentHead, Employee) are seeded using RoleManager.CreateAsync first.

14. Error Handling & User Feedback
BusinessRuleException — Service layer rule violation. GlobalFilter: sets TempData["Error"], redirects back.
NotFoundException — Entity not found. GlobalFilter: redirects to list view with error message.
UnauthorizedException — Missing or invalid claim. GlobalFilter: redirects to /Account/Login.
Access denied (wrong role): redirected to /Account/AccessDenied by cookie middleware.
Login lockout: show friendly message with time remaining. Do not reveal whether email exists (Forgot Password shows generic success message regardless).
All forms use server-side validation summaries. Client-side validation optional.
